## Sumário

## Contêineres

Vamos começar com os contêineres. Essa tecnologia revolucionou a forma de desenvolver e implantar aplicações, e hoje é um requisito fundamental para um desenvolvedor moderno.

Contêineres permitem empacotar uma solução e tudo o que ela precisa em uma imagem imutável, portátil e (se bem feita) leve.

> Como assim?

Bom, suponha que você tenha uma API em Node.js que recebe um vídeo por um endpoint e precisa convertê-lo para um formato compacto para uma análise de IA posterior (afinal ninguém merece gastar um monte de tokens com um vídeo em AVI de 5 segundos e 10GB).

E, para chamar o `ffmpeg` para fazer a conversão, você use o famoso `exec` do Node.js:

```javascript
import { exec } from 'child_process';

// Suponha que inputPath e outputPath estejam devidamente sanitizados e validados
export default async function convertToSmallVideoFormat(inputPath, outputPath) {
  const process = exec(
    `ffmpeg -i "${inputPath}" -c:v libx264 -preset fast -crf 28 "${outputPath}"`
  );

  await new Promise((resolve, reject) => {
    process.on("exit", code => {
      if (!code) {
        resolve();
      } else {
        reject(new Error(`ffmpeg exited with code ${code}`));
      }
    });
  })
}
```

Na tua máquina vai funcionar, já que o FFMpeg vai estar instalado e disponível no `PATH`. Mas... e se tu precisar rodar em uma plataforma diferente, como Azure Functions, um Web App ou em uma VM Windows?

Daí tu vai precisar instalar o FFMpeg na máquina, o que não é possível e muitas plataformas serverless, como Azure Functions.

Então, qual a solução? Contêineres! Tu pode criar uma imagem com o Node.js e o FFMpeg instalados, e rodar a tua API em qualquer lugar que aceite contêineres, que é o caso da maioria das plataformas modernas, incluindo as que citei acima.

Um container para esta solução seria algo assim:

```dockerfile
FROM node:24.15.0

WORKDIR /app

RUN apt-get update && apt-get install -y ffmpeg

COPY package.json package-lock.json ./
RUN npm ci

COPY . .

CMD ["npm", "start"]
```

Depois é só rodar um `docker build .` e a imagem estará prontinha para rodar em praticamente qualquer lugar.

> [!tip]
> O código acima foi simplificado para fins didáticos. Para uso em produção, sempre procure as boas práticas da linguagem e/ou framework que você estiver usando.

## O repositório

Com este breve resumo de contêineres, vem o ponto principal do artigo: o [container2wasm](https://github.com/container2wasm/container2wasm). Quando descobri ele fiquei pasmo, pois, teoricamente, ele permite rodar qualquer coisa diretamente do navegador, sem instalar nada.

Mas claro, nem tudo são flores. Mesmo com um computador bem potente, o contêiner vai rodar com uma performance péssima, então não dá pra dizer que a experiência do usuário vai ser a melhor do mundo (se tiver como o usuário ter uma experiência, pra começo de conversa).

Além disso, a não ser que tenha um servidor de proxy de rede, as chamadas HTTP de contêiner vão usar a função `fetch` do navegador, que traz o infame `CORS` pra jogada, bloqueando qualquer requisição cross-domain sem o cabeçalho `Access-Control-Allow-Origin` adequado.

Mas, chega de enrolar. Como fazer um contêiner rodar no navegador? Primeiramente, precisamos instalar a ferramenta a partir das [releases](https://github.com/container2wasm/container2wasm/releases/latest).

> [!tip]
> Para usuários Windows, é necessário usar o [WSL](https://learn.microsoft.com/pt-br/windows/wsl/install) ou outra forma de virtualização Linux, já que o container2wasm não tem suporte nativo para Windows. E para usuários do MacOS, existe uma [fórmula no Homebrew](https://formulae.brew.sh/formula/container2wasm) que deixa a instalação bem mais simples.

Depois de instalado e configurado no `PATH`, os comandos `c2w` e `c2w-net` devem estar disponíveis no terminal.

Agora, pegue uma imagem salva localmente, pode ser uma imagem criada com `docker build` ou uma imagem baixada com `docker pull`, e rode o seguinte comando:

```bash
c2w --to-js "<imagem>:<tag>" "<pasta de saída>/"
```

> [!important]
> Ao rodar a versão instalada via Homebrew, tive um erro de `git clone` ao fazer o build da imagem WASM. Pra resolver, adicionei esta flag: `--build-arg "SOURCE_REPO=https://github.com/container2wasm/container2wasm"`. Não tive o mesmo problema ao clonar o repositório e fazer o build manualmente em Go.

Com isso, uma imagem WASM será gerada, e será possível adicionar o contêiner a um site. Mas... como fazer isso?

## Rodando o contêiner WASM no navegador

Com os arquivos em mãos, é necessário criar um arquivo HTML que vá carregar o contêiner WASM. A [pasta de exemplos do projeto](https://github.com/container2wasm/container2wasm/tree/main/examples) contém uma boa referência. Para o caso de imagens usando a flag `--to-js` os exemplos de [`emscripten`](https://github.com/container2wasm/container2wasm/tree/main/examples/emscripten) e [`emscripten-simple`](https://github.com/container2wasm/container2wasm/tree/main/examples/emscripten-simple) são o melhor ponto de partida.

> E qual deles escolher?

A diferença entre eles é o **gerenciamento de rede**.

O `emscripten` permite que o contêiner se comunique com a internet por meio da API `fetch` do navegador, ou usando um WebSocket como proxy de rede (com o `c2w-net`, por exemplo).

Já o `emscripten-simple` não tem suporte a rede, e é mais simples de configurar.

Cada exemplo possui um `README.md` que mostra como criar uma imagem compatível e como configurar a rede, se necessário.

> [!important]
> Todas as instruções a seguir foram retiradas do [repositório](https://github.com/container2wasm/container2wasm) e podem ficar desatualizadas. Se for seguir estes passos, confira se não houve atualizações no repositório antes de prosseguir.

### Exemplo 1 - Neovim com o repositório de tipografia da LuzTech

Vamos começar pelo mais fácil primeiro. Este é o `Dockerfile` que criei para abrir o [Neovim](https://neovim.io/) diretamente na raíz do [repositório de tipografia da LuzTech](https://github.com/LuzTech-Development/Typography):

```dockerfile
FROM alpine:latest AS builder

RUN apk add --no-cache git

WORKDIR /workspace

RUN git clone "https://github.com/LuzTech-Development/Typography" .

RUN rm -rf .git

FROM alpine:latest AS runtime

RUN apk add --no-cache neovim

COPY --from=builder /workspace /workspace

WORKDIR /workspace

ENTRYPOINT ["nvim", "."]
```

Construí a imagem com o comando:

```bash
docker build --platform linux/amd64 -t nvim-demo:latest .
```

> [!tip]
> Eu adicionei a flag `--platform linux/amd64` para forçar a construção da imagem para a arquitetura x86_64, já que o [README do container2wasm](https://github.com/container2wasm/container2wasm/blob/ecb4caa499f19f1d5cfcddd43b80aa78f98e5102/README.md?plain=1#L36) recomenda esta arquitetura para diminuir as camadas de emulação.

Depois disso rodei o comando que descrevi [na seção acima](#o-repositório) para gerar os arquivos em WebAssembly.

Então copiei o [`index.html`](https://github.com/container2wasm/container2wasm/blob/main/examples/emscripten-simple/htdocs/index.html) do exemplo e adicionei o [Fit Addon para o XTerm.js](https://www.npmjs.com/package/@xterm/addon-fit) para o terminal ficar em tela cheia.

<details>
<summary>Ver index.html modificado</summary>

```html
<html>
  <head>
    <title>container2wasm: Neovim + LuzTech Typography</title>
    <link rel="stylesheet" href="./vendor/xterm.css" />
    <link rel="icon" type="image/svg+xml" href="/favicon.svg" />
    <style>
      html,
      body {
        width: 100%;
        height: 100%;
        margin: 0;
        overflow: hidden;
        background: #000;
      }

      #terminal {
        width: 100%;
        height: 100dvh;
      }
    </style>
  </head>
  <body>
    <div id="terminal"></div>
    <script src="./load.js"></script>
    <script type="module">
      import './vendor/xterm.js';
      import './vendor/xterm-pty.js';
      import { FitAddon } from './vendor/addon-fit.mjs';
      import './arg-module.js';
      import initEmscriptenModule from './out.js';

      const xterm = new Terminal();
      const fitAddon = new FitAddon();
      xterm.loadAddon(fitAddon);
      xterm.open(document.getElementById('terminal'));
      fitAddon.fit();

      const { master, slave } = openpty();

      xterm.loadAddon(master);

      Module.pty = slave;
      Module['mainScriptUrlOrBlob'] = new URL('./out.js', import.meta.url).href;

      // "/pack/info" file needs to be provided to the filesystem to start
      // the container. Refer to /cmd/init/main.go for the detail of info file.
      let info = 't:' + Math.round(new Date() / 1000) + '\n';
      Module['preRun'].push(mod => {
        try {
          FS.mkdir('/pack');
        } catch (e) {}
        mod.FS.writeFile('/pack/info', info);
      });
      var readableCallbacks = [];
      Module.pty.onReadable(() => {
        readableCallbacks.forEach(cb => cb());
        readableCallbacks = [];
      });
      Module['preRun'].push(Module => {
        Module['TTY'].stream_ops.poll = (stream, timeout, notifyCallback) => {
          if (Module.pty.readable) {
            return 1;
          }
          if (notifyCallback != null) {
            notifyCallback.registerCleanupFunc(() => {
              const i = readableCallbacks.indexOf(notifyCallback);
              if (i != -1) readableCallbacks.splice(i, 1);
            });
            readableCallbacks.push(notifyCallback);
          }
          return 0;
        };
      });

      const fitTerminal = () => fitAddon.fit();
      addEventListener('resize', fitTerminal);
      new ResizeObserver(fitTerminal).observe(
        document.getElementById('terminal')
      );

      (async () => {
        await initEmscriptenModule(Module);
        fitTerminal();
      })();
    </script>
  </body>
</html>
```
</details>

> [!note]
> As dependências são carregadas via CDN no `index.html` original, mas os cabeçalhos `Cross-Origin-Embedder-Policy` e `Cross-Origin-Opener-Policy` (obrigatórios para o container2wasm funcionar) podem causar inconsistência no download delas. Para evitar isso, baixei tudo para uma pasta `vendor/` ao lado do `index.html`.

<details>
<summary>Ver script para baixar dependências localmente</summary>

```bash

mkdir -p vendor
curl -fsSL "https://unpkg.com/@xterm/xterm@5.5.0/css/xterm.css" -o vendor/xterm.css
curl -fsSL "https://unpkg.com/xterm@5.3.0/lib/xterm.js" -o vendor/xterm.js
curl -fsSL "https://unpkg.com/xterm-pty/index.js" -o vendor/xterm-pty.js
curl -fsSL "https://esm.sh/@xterm/addon-fit@0.10.0/es2022/addon-fit.mjs" -o vendor/addon-fit.mjs
```

</details>

Por fim, para ver como ficou, rodei o comando [`serve` de Vercel](https://github.com/vercel/serve) com o seguinte arquivo `serve.json` na raíz:

```json
{
    "headers": [{
        "source": "**/*",
        "headers": [
            {
                "key": "Cross-Origin-Embedder-Policy",
                "value": "require-corp"
            }, {
                "key": "Cross-Origin-Opener-Policy",
                "value": "same-origin"
            }
        ]
    }]
}
```

> [!important]
> Estes cabeçalhos são obrigatórios para o sistema funcionar, porém eles causam outros problemas, como, no caso do blog, impedir que o Gravatar funcione ou causar inconsistências com o download de dependências de CDNs. Se for usar este repositório em algum projeto tenha isto em mente.

### Exemplo 2 - Caddy servindo o repositório de tipografia da LuzTech

Agora, indo pro exemplo mais difícil, vamos rodar o [Caddy](https://caddyserver.com/) no navegador, servindo o mesmo [repositório de tipografia da LuzTech](https://github.com/LuzTech-Development/Typography):

```dockerfile
FROM alpine:latest AS builder

RUN apk add --no-cache git

WORKDIR /build

RUN git clone --depth 1 "https://github.com/LuzTech-Development/Typography" /public && \
    rm -rf /public/.git

FROM alpine:latest AS runtime

RUN apk add --no-cache caddy

COPY --from=builder /public /public

ENV TERM=xterm-256color

EXPOSE 80

CMD ["caddy", "file-server", "--browse", "--listen", ":80", "--root", "/public"]
```

O comando de build da imagem e o arquivo `server.json` são os mesmos do [exemplo anterior](#exemplo-1---neovim-com-o-repositório-de-tipografia-da-luztech), o que muda são os arquivos estáticos, como o `index.html`, que agora vem a partir [desta pasta](https://github.com/container2wasm/container2wasm/blob/main/examples/emscripten/htdocs), também levemente modificado para usar o [Fit Addon para o XTerm.js](https://www.npmjs.com/package/@xterm/addon-fit) e ficar em tela cheia.

Com o HTML acima, ainda é necessário rodar o Webpack para criar um pacote com rede, e, para isto, criei um script levemente diferente do que existe no repositório original.

<details>
<summary>Ver script modificado</summary>

```bash
#!/bin/bash
set -euo pipefail

OUT_PATH="${1:-}"
CUSTOM_INDEX_HTML_PATH="${2:-}"
INITIAL_CWD="$PWD"

if [[ -z "$OUT_PATH" ]]; then
  echo "Usage: $0 <OUT_PATH> [CUSTOM_INDEX_HTML_PATH]" >&2
  exit 1
fi

if [[ "$OUT_PATH" != /* ]]; then
  OUT_PATH="$INITIAL_CWD/$OUT_PATH"
fi

if [[ -n "$CUSTOM_INDEX_HTML_PATH" ]]; then
  if [[ "$CUSTOM_INDEX_HTML_PATH" != /* ]]; then
    CUSTOM_INDEX_HTML_PATH="$INITIAL_CWD/$CUSTOM_INDEX_HTML_PATH"
  fi
  if [[ ! -f "$CUSTOM_INDEX_HTML_PATH" ]]; then
    echo "Custom index.html not found: $CUSTOM_INDEX_HTML_PATH" >&2
    exit 1
  fi
fi

mkdir -p "$OUT_PATH"

WORK=/tmp/c2w
DIST=/tmp/c2w-dist

rm -rf "$WORK" "$DIST"
mkdir -p "$WORK" "$DIST"

git clone -q https://github.com/container2wasm/container2wasm "$WORK"
cd "$WORK/examples/emscripten/htdocs"

cat > serve.json <<'JSON'
{
  "headers": [
    {
      "source": "**/*",
      "headers": [
        { "key": "Cross-Origin-Embedder-Policy", "value": "require-corp" },
        { "key": "Cross-Origin-Opener-Policy", "value": "same-origin" }
      ]
    }
  ]
}
JSON

if [[ -n "$CUSTOM_INDEX_HTML_PATH" ]]; then
  rm -f index.html
  cp "$CUSTOM_INDEX_HTML_PATH" ./index.html
fi

npm install --no-audit --no-fund
npx --no-install webpack

curl -fsSL "https://unpkg.com/xterm@5.3.0/lib/xterm.js" -o vendor/xterm.js
curl -fsSL "https://unpkg.com/xterm-pty/index.js" -o vendor/xterm-pty.js
curl -fsSL "https://esm.sh/@xterm/addon-fit@0.10.0/es2022/addon-fit.mjs" -o vendor/addon-fit.mjs

cp -R index.html dist vendor "$DIST"/

C2W_TAG="$(c2w --version | awk '{ print "v" $3 }')"
curl -fsSL "https://github.com/container2wasm/container2wasm/releases/download/${C2W_TAG}/c2w-net-proxy.wasm" \
  | gzip > "$DIST/c2w-net-proxy.wasm.gzip"

cp -R "$DIST"/. "$OUT_PATH"/

rm -rf "$DIST" "$WORK"
```

</details>

> [!note]
> Usei este script para usar o [`serve` da Vercel](https://github.com/vercel/serve) em vez de rodar um contêiner com o Apache, além disso o script baixa o `c2w-net-proxy.wasm` da release com a mesma versão do `c2w` que está instalada na máquina, o que evita problemas de incompatibilidade. Também não é necessário baixar as dependências manualmente como no [exemplo anterior](#exemplo-1---neovim-com-o-repositório-de-tipografia-da-luztech), já que o script de build faz isso automaticamente.
